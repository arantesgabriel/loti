# Human Inputs / Genuine Blockers

The implementation agent should not invent identities or production data.

## Production member identities

For each initial member (Gabriel, Brunna, Amanda, Bola and Vinicius), production bootstrap requires:

- the member's actual email address;
- the initial password or the approved secure bootstrap process.

Real production addresses and passwords are not part of this specification. Do not promote `@loti.test` seed accounts to production.

## Production configuration

- `BETTER_AUTH_SECRET` must be a strong server-side secret; it can be generated by operator tooling.
- `BETTER_AUTH_URL` must use the final Vercel HTTPS origin.
- `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` must belong to the intended environment/database.
- Creating Turso database auth tokens and granting Vercel access to the private GitHub repository require explicit confirmation at the point of the security-sensitive action.

## Legacy migration

- Map workbook person labels to the real Better Auth users created in production.

## Infrastructure

The canonical target is Vercel + Turso/libSQL. Production does not use Railway or a persistent application volume. If the authenticated accounts cannot create the required resources, record the exact external permission blocker and finish all repository-side work.

Creating the `loti-prod` and `loti-dev` databases is within the deployment request. Do not create or reveal database credentials until their scope and storage destination have been confirmed. Store approved credentials only as server-side Vercel environment variables (or in a protected local operator environment).

## What is not a blocker

Do not stop for ordinary code errors, migration failures, tests, or naming already resolved by the canonical specification. Fix those and continue.
